# Taste — Coding Style

- No hardcoded colors — use design tokens (brand ink/gold/cream). Confidence: 0.85
- Uses Solar BoldDuotone icons (`weight="BoldDuotone"`), not lucide-react. Confidence: 0.85
- No `any` type; no `console.log` (only `console.error` in catch). Confidence: 0.8
- Explicit return types on exported functions. Confidence: 0.7
- Do not edit `components/ui/*` (shadcn-generated). Confidence: 0.8
- Rate limiting before DB work on every endpoint. Confidence: 0.75
- Prisma Neon HTTP array-form `$transaction([...])` only (no callback form, no createMany). Confidence: 0.7
- Tables: horizontally scrollable, wrap cell text instead of truncating, match the existing booking-wedding table style. Confidence: 0.7
- Prefers hardcoded options for small known filter sets over deriving from the API response; dropdowns over chip filters. Confidence: 0.65
- Prefers right-side slide-in drawers for list→detail views (e.g., conversation detail) over navigating to a separate page or a centered modal. Confidence: 0.7
- Navigation depth follows data cardinality: a row mapping to one detail goes straight to it, but a row with many sub-items (e.g., a sales row → multiple conversations) keeps an intermediate list drawer before the detail/dump. Confidence: 0.7
- Prefers shared/general entities (like Vendor) to live under the `(general)` route group rather than nested under a specific domain module (like `purchase`). Confidence: 0.8
- Keeps permission-related layers in sync — module→permission registry, seeders, migration SQL, and page-level permission maps — and expects every layer updated (and the seeder/migration actually applied to the DB) together whenever a feature moves modules or a role's permissions change. Confidence: 0.75
- Prefers status/stage badges and labels to use the actual color from the source system (e.g., Bitrix `stageColor`) with auto-computed readable text contrast, rather than generic semantic color mappings. Confidence: 0.7
- Prefers referencing external-system records (e.g., a Bitrix deal looked up by client name) through a searchable dropdown showing context (PIC + status/stage), instead of manually typing a raw ID. Confidence: 0.7
- Prefers reusing existing components over building new ones — e.g., "pake komponent yang sudah ada" when a filter needs a search dropdown, so the existing `SearchableSelect` is used for consistency with other screens. Confidence: 0.8
- Prefers filter/search fields (e.g., "filter by sales") to be searchable dropdowns rather than plain `Select` inputs. Confidence: 0.7
- For data export on overview/dashboard screens, prefers a single "Export" button that opens a dropdown with format choices (PDF and Excel), rather than a single fixed format or separate buttons. Confidence: 0.7
- For Excel exports with multiple data sections, prefers a multi-sheet workbook (each section like "Sumber Iklan" on its own sheet) rather than stacking all sections on one sheet. Confidence: 0.7
- In header/action bars, prefers action buttons like Export to be grouped with the Filter control on the left side (placed before Filter), keeping Refresh on the right. Confidence: 0.55
- Prefers export output to reflect the currently filtered/displayed data (active date range + search/filter query), and expects the same Export dropdown (PDF/Excel) pattern to be reused across report/list pages (e.g., Response Sales, Percakapan), not just the Overview dashboard. Confidence: 0.8
- Prefers PDF export to be available broadly, including flat tabular/list pages (e.g., Transaksi/deals) — asked to add PDF there ("kalo export pake PDF bisa bro?") after initially requesting Excel-only, so list pages also get the PDF + Excel dropdown. Confidence: 0.75
- Prefers PDF exports to be compact rather than exhaustive — drop verbose/non-essential columns (e.g., long ad copy fields like Ads URL/Headline/Body) so the document stays short and readable, keeping full detail in the Excel export instead. Confidence: 0.7
- Flags runaway/continuous repeated requests (e.g., polling that keeps re-hitting the same route) as a problem to diagnose and reduce, not acceptable background behavior. Confidence: 0.6
- When background polling is too aggressive, prefers reducing its aggressiveness (disable refetch-on-window-focus, add staleTime/cache) over removing the polling feature entirely. Confidence: 0.6
- Prefers feature/UI parity across sibling report pages — when a filter exists on one page (e.g., "Tanggal Dibuat" elsewhere in Bitrix), expects it replicated on related pages like Percakapan. Confidence: 0.6
- For date-range filters, uses a Calendar component (react-day-picker, `mode="range"`) inside the filter panel with a "Bersihkan" clear button, and propagates the range to exports too. Confidence: 0.6
- For date-range filtering against Bitrix datetime fields, uses an inclusive start (`>=CREATED` at T00:00:00) and an exclusive next-day end (`<CREATED` at the following day's T00:00:00). Confidence: 0.55
- Converts picked calendar dates to local calendar day via date-fns `format(d, "yyyy-MM-dd")` rather than `toISOString()` to avoid the UTC off-by-one. Confidence: 0.55
- When a filter criterion isn't directly queryable on the list entity in the source system (e.g., transfer history lives in session history, not on the activity row), derives the field server-side from a secondary source and applies the filter post-fetch (with the total re-counted), keeping the pattern consistent with sibling pages. Confidence: 0.6
- Surfaces derived boolean/count state (e.g., number of transfers) as an inline badge next to the primary status badge in list tables. Confidence: 0.55
- Prefers date-range filters on list/report pages to default to the current day (from = to = today, midnight-local) rather than being empty/unset, and Reset should return to today too, not clear to empty. Confidence: 0.55
- When a feature must be accessible to all roles, prefers isolating it behind its own dedicated permission module (e.g., `attendance:view`) rather than granting a broad domain permission like `hr:view` to everyone, so granting the feature doesn't unlock the entire domain world. Confidence: 0.7
- Granting a permission to a role alone isn't enough to make a feature visible — the sidebar/nav entry must also sit in a route group that role can access. A feature meant for all roles must be moved out of the domain-restricted nav group (e.g., HRD) into `(general)`, otherwise non-domain roles still won't see the menu even with the grant. Confidence: 0.65
- Resolves external-system user IDs to human-readable names in list/detail UI (transfer events, system mentions) instead of showing raw IDs, with a `#id` fallback when the source payload lacks a name. Confidence: 0.6
- When the primary source payload omits a name for an external-system ID, digs the name out of a secondary source first (e.g., scraping `[USER=id]Name[/USER]` tags from raw system message text) before accepting a raw-ID fallback — so names still resolve even for duplicate/multiple transfers. Confidence: 0.65
- Renders untrusted BBCode/message text without `dangerouslySetInnerHTML` — tokenizes into plain strings + React elements so message content stays inert. Confidence: 0.55
- For conversation/message timelines, prefers a chat-app bubble layout — customer messages left-aligned, agent/sales messages right-aligned (distinct colors per side) — while system/notification messages (assign/transfer/status) are plain centered muted text with no bubble. Confidence: 0.8
- Prefers a confirmation modal with a warning before irreversible/finalizing actions (e.g., submitting a signed agreement), stating the consequences (fields become locked, changes require re-approval) before proceeding. Confidence: 0.65
- Wants warning/confirmation modals for irreversible actions to look intentionally intimidating/"scary" so the user is forced to read them — danger-triangle icon in a red circle, red/destructive border + background warning box, a bold "Peringatan:" label, and a destructive (red) confirm button — rather than a neutral confirm dialog. Confidence: 0.75
- Wants that same scary warning/confirmation gate applied uniformly across the entire approval workflow — manager, finance, and sales approvals plus the create/edit booking drawers — not just the client agreement, so every consequential/irreversible action (approve, create, edit/finalize) forces the user to read before proceeding. Confidence: 0.8
- When a key warning point (e.g., re-approval requires the Manager's signature to be re-approved) is added to one approval modal, expects the same copy mirrored into every other approval-related modal (approve, create, edit) so the wording stays consistent — not just the single modal being edited. Confidence: 0.6
- Wants the project to lint clean with zero warnings — runs `npm run lint` and expects even `@typescript-eslint/no-unused-vars` warnings (unused imports and assigned-but-unused vars) to be removed rather than left as warnings. Confidence: 0.6
- Prefers hiding/disabling a feature rather than deleting its code — "hide dulu featurenya" keeps the implementation intact and reversible for later re-enable, instead of removing it. Confidence: 0.6
- Prefers TanStack Query for client-side data fetching with a 30-second cache/polling TTL (`staleTime` + `refetchInterval` = 30s) rather than manual `useEffect`+`fetch`, so the UI re-hits the source only after the TTL window. Confidence: 0.7
- Prefers a single general overview at `/` over per-module overview pages; on first landing there should be no module picker, defaulting straight into the booking module. Confidence: 0.6
- Prefers the Overview and BITRIX24 menus pinned to the top of the sidebar, above the world/module nav. Confidence: 0.55
- Prefers mirroring the source system's exact field/column structure and labels (e.g., splitting Bitrix's "Sumber" and "Informasi sumber" into two separate columns) rather than merging distinct source fields into one display column. Confidence: 0.5
- Prefers breakdown/summary cards that carry multiple numeric metrics per row (Kantor/Mandiri/Sudah-dibalas/Belum-dibalas) to be rendered as a table with one column per metric, rather than a bar/percentage list — and the table should be grouped per salesperson (per sales), not per source/channel. Confidence: 0.8
- Prefers certain overview/dashboard sections (e.g., "Sumber Iklan") to be full-width rather than forced into a 2-column grid. Confidence: 0.7
- Prefers "Sumber Database" to stay a simple bar-list card paired in the same 2-column grid as the Venue section (not full-width, not a table) — full-width treatment is reserved for other sections like "Sumber Iklan". Confidence: 0.6
- Cares about backend performance and dislikes N+1 query patterns — flags slow endpoints and expects batched queries (a constant number of round-trips per concern) instead of per-row/per-group loops. Confidence: 0.8
- Prefers aggregating counts/sums in the database (Prisma `groupBy` / `$queryRaw`) rather than loading many rows into JS and counting them there. Confidence: 0.7
- Prefers reading auth-derived flags/data (e.g., `isSuperAdmin`, `dataScope`) from the session/JWT instead of re-querying the DB (role table, `profile.findUnique`) on every request. Confidence: 0.65
- Prefers server-side dedup (`distinct`) over arbitrary row caps (`take: 500`) when collecting a candidate set, so qualifying rows aren't silently truncated. Confidence: 0.55
- Prefers table column headers to be explicit and self-describing so meaning is clear without surrounding context — e.g., "DB Kantor"/"DB Mandiri" instead of just "Kantor"/"Mandiri", and "Sudah FU"/"Belum FU" instead of "Sudah"/"Belum". Confidence: 0.6
- Prefers shimmer skeleton loading states (the shadcn `Skeleton` component) for dashboard/overview sections while data loads — replacing "…" placeholders and ad-hoc `animate-pulse rounded-xl bg-muted` div blocks. Confidence: 0.7
- Prefers independent server-side data loads (e.g., dashboard aggregate, calendar events, group-members scope) to be fired in parallel via `Promise.all` rather than sequential `await`s, so inline page fetches don't block each other in a waterfall. Confidence: 0.7
- For slow Prisma/Postgres queries that filter on multiple columns (status + date range and/or owner/scope ID), prefers adding composite indexes to the schema (e.g., `[recordStatus, createdAt]`, `[recordStatus, salesId]`) via a migration rather than leaving single-column indexes that force scans. Confidence: 0.6
